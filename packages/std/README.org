* Bassline Std

#+ATTR_HTML: :width 600px
[[./docs/images/dog.jpg]]

This is our "standard library" for Bassline. It's contains useful
higher level tools / dialects for working with Bassline, all built
from what =core= exposes.

You can use this as a reference / cookbook for the kinds of things you
can build with Bassline.

* What's Included

** A wire dialect

=wire.js= exports mold & load.

These let us represent messages (possibly nested) and their
capabilities over the wire, letting us recognize and use remote caps
as well as share our local caps.

=mold(aMsg, mindId)= takes a message and a fn to encode a cap as a data
value for dispatching. This is used to lower a message with caps into
raw JSON data (often just a uuid, but it can support whatever), to be sent
over the wire, or placed into a new message.

To disambiguate messaages from dictionaries, the form mold normalizes
into a "load form". A load form is a dictionary with a single key:
={loadMessage: {data, caps}}=.

=load(aMsg, resolveCap)= does the opposite of mold. It takes a message
and if it has no caps and it's data is a load form, it will recursively
traverse and rewrite the nested messages, using resolveId to bind the
caps on the messages, and unwrap it's data.

** A context system

To make the wire dialect useful, we want a mechanism to park caps
before going over the wire, as well as dispatching to parked caps.

That's exactly what this exports.

=context= is a factory for the internal pieces.

=conversation= let's us reuse a context when talking with
something. Letting remote caps work like local caps.

=dialogue= let's us make a context implicit, only it's effectively a
conversation without sharing.

** A proper lambda abstraction

Within =lambda.js= we export =lambda=.

=lambda= let's us convert any unary function into an invocable =LAMBDA=
message.

=lambda= properly handles curried functions and closures, wrapping any
returned function as a =LAMBDA= message.

=lambda= expects it's function to return either a function, message, or
undefined, which it converts into an empty message.

This let's us build any kind of RPC protocol, but supporting proper
higher order functions rather than terminal data responses. It also
let's us build "rpc" protocols that have closure over their
interactions, reducing schema boilerplate.

* Dialect Messages

Within std we define a few kinds of messages and their expected cap
behaviors.

** REQUEST

A =REQUEST= is a message with caps: =resolve= and =reject=.

A =REQUEST= expresses the same semantics as JS Promises. Meaning resolve
& reject are idempotent and whichever fires first resolves the
promise.

A =REQUEST= should be used to express a request with a discrete answer,
as opposed to something with multiple potential answers.

It can be thought of as a degenerate =send= that closes after a single response.

** LAMBDA

A =LAMBDA= is something with a cap =call=.

A =LAMBDA= expresses semantics of a function that takes a =REQUEST= as
input, and resolves with a message. The resolved message may itself be
another =LAMBDA=, allowing us to express higher order functions as messages.
