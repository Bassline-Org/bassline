* Introduction
This literate document contains the source code for the core of [[https://bassline.dev][Bassline]] v2.

Bassline is designed to be hacked on and modified, so we encourage people to read this!

** TLDR
Bassline is a system for partial information programming.

Programs in Bassline work from incomplete messages. They build local understanding from what they have, act on new information, and continue.

Anything outside your local perspective is encountered through communication. When that communication yields information that matters, we observe it as a resource. We do not need a complete account of what it is, where it is, or how it produces what we receive.

Identity, location, provenance, timing, order, and sameness are therefore not taken as settled facts. They are judgments made from partial information, and different participants may have different grounds for believing them.

And because the model never assumes a closed world, growth uses the same mechanism as ordinary operation. New message shapes, participants, and behavior do not require a separate extensibility system. They arrive as more messages to interpret.

* The Kernel

The kernel here starts with messages and a local capability for communication. In this book that capability is implemented with reader/writer pairs backed by channels. The important thing is the ability to exchange and observe information, not the queue or the exact interface shape.

For each part of the kernel, we will separate the abstract idea from the concrete implementation used in this book. The abstract layer explains what shape of thing we are modeling. The concrete layer shows one minimal JavaScript realization of that shape.

** Messages
:PROPERTIES:
:header-args: :tangle ../src/messages.js
:END:

*** Abstractly

A message is a fragment of partial information. It is whatever can be locally held, passed around, inspected, and combined without requiring a complete picture of the world.

A message does not come with privileged meaning beyond what participants give it. If provenance, correlation, naming, coordination hints, or other structure matters, it lives in the message like any other data. This is important because Bassline does not want a separate metadata plane that is somehow more real than the information being exchanged.

*** Concretely

A message is a plain object with string keys. It can be empty, partially filled, or nested inside other messages.

The concrete representation is intentionally minimal. Plain objects are open-ended, nest naturally, and are easy to serialize, enrich, and inspect. That keeps the message lightweight and avoids forcing a closed protocol up front.

=message()= normalizes its input: plain objects pass through, =undefined= becomes ={}=, and anything else is wrapped as ={body: value}=.

=update= is auto-curried. With two arguments =(msg, fn)= it returns a new message. With one argument =(fn)= it returns a transform you can pass to =.map()=.

#+begin_src js
import { isPlainObject } from './utils.js'

export const message = content => {
  if (content === undefined) return {}
  if (isPlainObject(content)) return { ...content }
  return { body: content }
}

export function updateWith(msg, fn) {
  return {...msg, ...fn(msg)}
}

export function update(...args) {
  if (args.length === 1) {
    const [fn] = args;
    return msg => updateWith(msg, fn)
  }
  if (args.length === 2) {
    const [msg, fn] = args
    return updateWith(msg, fn)
  }
  throw new Error(`invalid update arity: ${args.length}`)
}

export const isEmpty = msg => Object.keys(msg).length === 0
#+end_src

*** Exception Messages
We cannot expect our systems to run smoothly, which is why we define these messages.

These indicate that some exceptional state has ocurred while processing a message.

Even here, Bassline stays in the same conceptual world. Warnings and faults are still expressed as messages because exceptional states are still partial information that must be communicated and interpreted.

For now we define two kinds of exceptional states.
| condition | what it means                                |
|-----------+----------------------------------------------|
| Warning   | It's workable, but you should know something |
| Fault     | Something went wrong, and I cannot continue  |
**** Non Fatal Exceptions: Warnings

This means that something was able to complete what it needed to, but it has something to say about how it could be done better, or some remark on if there is a better way of doing it.

#+begin_src js
export const warning = reason => message({type: 'warning', body: reason})
#+end_src

**** Fatal Errors: Fault
This indicates that processing cannot continue, and we must stop.

Unlike warnings, which are used to annotate the message being processed, we throw the fault message.

#+begin_src js
export class Fault extends Error {
  constructor(condition, msg, context = {}) {
    super(`fault: ${condition}`)
    this.condition = condition;
    this.msg = msg;
    this.context = context;
  }
}
export const fault = (condition, msg, context) => {
  throw new Fault(condition, msg, context)
}
#+end_src

** Communication
:PROPERTIES:
:header-args: :tangle ../src/channel.js
:END:

*** Abstractly

Communication is the local capability to receive new information and contribute new information. Bassline does not start from a rigid request-response model, because that assumes too much structure too early. Instead, communication is ongoing, and participants coordinate by processing messages and inferring enough structure from what they know to continue.

Communication needs a shape that preserves decoupling. Producers should be able to contribute information without needing a fixed understanding of every consumer, and consumers should be able to build their own understanding from the flow they observe.

*** Concretely

In this book, communication is exposed as a =[reader, writer]= pair. The reader consumes arriving messages. The writer contributes messages. Together they let producers and consumers stay decoupled while still participating in the same flow of information.

That pair is implemented with channels. Calling =channel()= returns a =[reader, writer]= pair. The writer pushes values in; the reader consumes them through combinators. =sink= is the primary way to consume a reader. It drives the reader and calls a function for each value. Every combinator (=map=, =filter=, =scan=, etc.) returns a new reader with the same combinator methods, so pipelines compose naturally.

Coordination is not a special subsystem layered on top of this. It is what happens when participants interpret messages, infer enough structure to proceed, and respond from what they know. If something protocol-like emerges, it does so as a stable pattern in message flow, not as a privileged runtime concept.

*** Channel Implementation

The concrete implementation here uses channel classes that manage a queue of values with a set of waiting consumers. When a value is written and someone is waiting, it resolves immediately. Otherwise it buffers. This implementation is single-consumer: calling =consume()= more than once throws.

Users do not touch these classes directly. The factories below return =[reader, writer]= pairs that hide the internals.

#+begin_src js
export const ERR = Symbol.for('channel.err')
export const WAITING = Symbol.for('channel.waiting')
export const CLOSED = Symbol.for('channel.closed')

export class ConsumedChannelError extends Error {
  constructor() {
    super('Cannot consume a channel more than once!')
  }
}

export class Channel {
  queue = []
  waiters = []
  state = WAITING
  consumed = false
  error = null

  write(value) {
    if (this.state === CLOSED || this.state === ERR) return
    if (this.waiters.length > 0) this.waiters.shift().resolve({ value, done: false })
    else this.queue.push(value)
  }
  close() {
    if (this.state !== WAITING) return
    this.state = CLOSED
    for (const w of this.waiters) w.resolve({ value: undefined, done: true })
    this.waiters.length = 0
  }
  err(e) {
    if (this.state !== WAITING) return
    this.state = ERR
    this.error = e
    if (this.queue.length === 0) {
      for (const w of this.waiters) w.reject(e)
      this.waiters.length = 0
    }
  }
  consume() {
    if (this.consumed) throw new ConsumedChannelError()
    this.consumed = true
    return {
      [Symbol.asyncIterator]: () => ({
        next: () => {
          if (this.queue.length > 0) return Promise.resolve({ value: this.queue.shift(), done: false })
          if (this.state === ERR) return Promise.reject(this.error)
          if (this.state === CLOSED) return Promise.resolve({ value: undefined, done: true })
          return new Promise((resolve, reject) => this.waiters.push({ resolve, reject }))
        },
        return: (value) => {
          this.close()
          return Promise.resolve({ value, done: true })
        },
        throw: (e) => {
          this.err(e)
          return Promise.resolve({value: e, done: true })
        }
      }),
    }
  }
  send(...values) {
    values.forEach(v => this.write(v))
  }
  reader() {
    const reader = {
      consume: () => this.consume(),
      sink: fn => sink(reader, fn),
      map: fn => map(reader, fn),
      filter: fn => filter(reader, fn),
      tee: count => tee(reader, count),
      take: n => take(reader, n),
      scan: (fn, seed) => scan(reader, fn, seed),
      tap: fn => reader.map(v => (fn(v), v)),
      thru: cb => cb(reader),
      merge: readers => merge([reader, ...readers]),
    }
    return reader
  }
  writer() {
    const writer = {
      send: (...values) => this.send(...values),
      close: () => this.close(),
      err: e => this.err(e),
    }
    return writer
  }
}

export class SlidingChannel extends Channel {
  constructor(size = 1) {
    super()
    this.size = size
  }
  write(value) {
    if (this.state === CLOSED || this.state === ERR) return
    if (this.waiters.length > 0) this.waiters.shift().resolve({ value, done: false })
    else {
      while (this.queue.length >= this.size) this.queue.shift()
      this.queue.push(value)
    }
  }
}

export class ClockChannel extends SlidingChannel {
  constructor(ms, size = 1) {
    super(size);
    this.interval = setInterval(() => this.write(Date.now()), ms)
  }
  close() {
    clearInterval(this.interval)
    super.close()
  }
  err(e) {
    clearInterval(this.interval)
    super.err(e)
  }
  writer() {
    const w = super.writer();
    return {close: w.close}
  }
}
#+end_src

*** Factories

The factories are the public API. Each returns a =[reader, writer]= pair.

- =channel()= : unbounded queue
- =slidingChannel(size)= : bounded queue that drops the oldest value when full
- =clock(ms, size)= : sliding channel that emits =Date.now()= on an interval

#+begin_src js
export const channel = () => {
  const chan = new Channel()
  return [chan.reader(), chan.writer()]
}

export const slidingChannel = (size = 1) => {
  const chan = new SlidingChannel(size)
  return [chan.reader(), chan.writer()]
}

export const clock = (ms = 1000, size = 1) => {
  const chan = new ClockChannel(ms, size)
  return [chan.reader(), chan.writer()]
}
#+end_src

*** Combinators

Combinators transform readers into new readers. Every reader object has these as methods (=reader.map(fn)=, =reader.filter(fn)=, etc.), and the returned reader has them too, so they chain.

**** =sink(reader, fn)=

The terminal combinator. Consumes every value from the reader, calling =fn= for each one. Returns a promise that resolves when the reader closes.

#+begin_src js
export async function sink(reader, fn) {
  for await (const val of reader.consume()) {
    await fn(val)
  }
}
#+end_src

**** =map(reader, fn)=

Transforms each value through =fn=. The function can be async. Returns a new reader of the transformed values.

#+begin_src js
export function map(reader, fn) {
  const [out, writer] = channel()
  reader
    .sink(async v => writer.send(await fn(v)))
    .then(writer.close)
    .catch(writer.err)
  return out
}
#+end_src

**** =filter(reader, fn)=

Keeps only values for which =fn= returns truthy. The predicate can be async.

#+begin_src js
export function filter(reader, fn) {
  const [out, writer] = channel()
  reader
    .sink(async v => {
      if (await fn(v)) writer.send(v)
    })
    .then(writer.close)
    .catch(writer.err)
  return out
}
#+end_src

**** =tee(reader, count)=

Splits one reader into =count= independent readers. Every value is sent to all of them.

#+begin_src js
export function tee(reader, count = 2) {
  const channels = []
  for (let i = 0; i < count; i++) channels.push(channel())
  reader
    .sink(v => channels.forEach(([_, write]) => write.send(v)))
    .then(() => channels.forEach(([_, write]) => write.close()))
    .catch(e => channels.forEach(([_, write]) => write.err(e)))
  return channels.map(([read, _]) => read)
}
#+end_src

**** =take(reader, n)=

Reads at most =n= values from the reader, then closes.

#+begin_src js
export function take(reader, n = 10) {
  if (typeof n !== 'number' || n < 1) throw new Error('invalid take: ' + n)
  const [out, writer] = channel()
  ;(async () => {
    try {
      let count = 0
      for await (const v of reader.consume()) {
        writer.send(v)
        if (++count >= n) break
      }
      writer.close()
    } catch (e) {
      writer.err(e)
    }
  })()
  return out
}
#+end_src

**** =scan(reader, fn, seed)=

Accumulates values. Like =Array.reduce=, but emits each intermediate result. =fn(accumulator, value)= returns the next accumulator, which is sent downstream.

#+begin_src js
export function scan(reader, fn, seed) {
  const [out, write] = channel()
  let last = seed
  reader
    .sink(async v => {
      last = await fn(last, v)
      write.send(last)
    })
    .then(write.close)
    .catch(write.err)
  return out
}
#+end_src

**** =merge(readers)=

Combines multiple readers into one. Values arrive in whatever order the sources produce them. Closes when all sources close.

#+begin_src js
export function merge(readers) {
  const [out, write] = channel()
  Promise.all(readers.map(r => r.sink(write.send)))
    .then(write.close)
    .catch(write.err)
  return out
}
#+end_src

Readers also have two convenience methods that aren't standalone functions:

- =tap(fn)= : like =map=, but runs =fn= for its side effect and passes the value through unchanged
- =thru(cb)= : passes the reader itself to =cb= and returns whatever =cb= returns. This is the extension point for user-defined combinators.

*** User-level Combinators

The =thru= method on readers lets users build their own combinators as simple functions from reader to reader. Here are some examples.

#+begin_src js :tangle ../examples/channel-example.js
import { channel, merge } from "../src/channels.js"

const timeout = ms => new Promise(res => setTimeout(res, ms))

export const debounce = (ms = 300) => reader => reader.map(async v => {
  await timeout(ms);
  return v
})

export const dedup = (diff, seed) => reader => {
  const compare = diff ?? ((acc, curr) => acc !== curr);
  let last = seed;
  return reader.filter(async v => {
    const res = await compare(last, v)
    if(res) {
      last = v
    }
    return res
  })
}

export const max = (seed = 0) => reader => reader
      .filter(v => typeof v === 'number')
      .scan((acc, curr) => acc > curr ? acc : curr, seed)
      .thru(dedup(null, seed))

const [r, w] = channel()
w.send(1,2,3,4,5,6,7,7,7,7,8,9,10);
w.close()

let count = 0;
await merge(r.tee(100))
  .tap(() => count++)
  .thru(max())
  .sink(console.log)

console.log(count)
#+end_src

=debounce=, =dedup=, and =max= all follow the same shape: a configuration function that returns a =reader → reader= transform, suitable for =thru=.

* Transports

As above, it helps to separate the abstract role of a transport from the concrete transport used in this book.

** Abstractly

A transport adapts some external medium into local communication capabilities. This matters because the programming model should not change just because information crossed a process boundary, a machine boundary, or a device boundary. Local and non-local communication differ in mechanics, but they should not require different conceptual tools.

** Concretely

Every transport produces the same thing: a =[reader, writer]= pair. What differs is the medium underneath and whether that medium carries raw bytes or discrete messages.

Byte transports (TCP sockets, stdio, serial) carry raw chunks. They need a framing layer to delimit and parse messages. Message transports (WebSocket, WebWorker/MessagePort) carry discrete messages natively and skip framing entirely.

*** Framing
:PROPERTIES:
:header-args: :tangle ../src/frame/jsonl.js
:END:

Framing is separated from any specific transport. =readFrame= is a =reader → reader= transform: it accumulates chunks, splits on newlines, and parses each line as JSON. =writeFrame= is a plain function that serializes a message as a JSON line.

#+begin_src js
import { message } from '../messages.js'
import { channel } from '../channel.js'

export const readFrame = reader => {
  const [out, write] = channel()
  let buffer = ''
  reader
    .sink(chunk => {
      buffer += chunk
      let nl
      while ((nl = buffer.indexOf('\n')) !== -1) {
        const line = buffer.slice(0, nl)
        buffer = buffer.slice(nl + 1)
        if (!line) continue
        try { write.send(message(JSON.parse(line))) }
        catch (e) { console.error('readFrame parse error: ', e)}
      }
    })
    .then(write.close)
    .catch(write.err)
  return out
}

export const writeFrame = msg => JSON.stringify(msg) + '\n'
#+end_src

=readFrame= is not a =scan= because one input chunk may produce zero or many messages. It uses =sink= internally to feed a new channel. =writeFrame= is used as =.map(writeFrame)= on the outgoing side.

*** Socket
:PROPERTIES:
:header-args: :tangle ../src/transports/socket.js
:END:

A socket is a byte transport. =fromSocket= adapts a Node.js socket into a =[reader, writer]= pair by wiring socket events to channels on the read side and piping through =writeFrame= on the write side. =readFrame= parses the incoming chunks.

#+begin_src js
import net from 'node:net'
import { channel } from '../channel.js'
import { readFrame, writeFrame } from '../frame/jsonl.js'

export function fromSocket(socket) {
  const [read, write] = channel()
  socket.on('data', chunk => write.send(chunk.toString()))
  socket.on('close', () => write.close())
  socket.on('error', e => write.err(e))

  const [outRead, outWrite] = channel()
  outRead
    .map(writeFrame)
    .sink(data => socket.write(data))
    .then(() => socket.destroy())
    .catch(e => socket.destroy(e))
  socket.on('close', outWrite.close)
  socket.on('error', outWrite.err)

  return [read.thru(readFrame), outWrite]
}

export function connect(options = {}) {
  return fromSocket(net.createConnection(options))
}
#+end_src

*** Serving
:PROPERTIES:
:header-args: :tangle ../src/transports/server.js
:END:

A server listens on a socket and produces a reader of connections. Each connection is itself a =[reader, writer]= pair, produced by =fromSocket=.

#+begin_src js
import net from 'node:net'
import { fromSocket } from './socket.js'
import { channel } from '../channel.js'

export function serve(options = {}) {
  const [r, w] = channel()
  const server = net.createServer(socket => {
    w.send(fromSocket(socket))
  })
  server.listen(options)
  server.on('close', w.close)
  server.on('error', w.err)
  return [r, server]
}
#+end_src

*** WebSocket
:PROPERTIES:
:header-args: :tangle ../src/transports/websocket.js
:END:

A WebSocket is a message transport. Each =ws.send()= is one discrete message, so no framing is needed — just JSON encode/decode. This works in the browser with native =WebSocket=, in Node.js with the =ws= package, and for =RTCDataChannel= (same event interface).

#+begin_src js
import { channel } from '../channel.js'
import { message } from '../messages.js'

export function fromWebSocket(ws) {
  const [read, write] = channel()
  ws.addEventListener('message', e => {
    try { write.send(message(JSON.parse(e.data))) }
    catch (e) { console.error('failed to send: ', e)}
  })
  ws.addEventListener('close', () => write.close())
  ws.addEventListener('error', e => write.err(e))

  const [outRead, outWrite] = channel()
  outRead
    .sink(v => ws.send(JSON.stringify(v)))
    .then(outWrite.close)
    .catch(outWrite.err)

  return [read, outWrite]
}
#+end_src

*** WebWorker
:PROPERTIES:
:header-args: :tangle ../src/transports/worker.js
:END:

A =MessagePort= is a message transport that uses structured clone — objects cross the boundary without serialization. Works with =Worker=, =MessagePort=, =SharedWorker.port=, and =BroadcastChannel=.

#+begin_src js
import { channel } from '../channel.js'
import { message } from '../messages.js'

export function fromPort(port) {
  const [read, write] = channel()
  port.onmessage = e => write.send(message(e.data))
  port.onmessageerror = e => write.err(e)

  const [outRead, outWrite] = channel()
  outRead
    .sink(v => port.postMessage(v))
    .then(outWrite.close)
    .catch(outWrite.err)

  return [read, outWrite]
}
#+end_src

*** Stdio
:PROPERTIES:
:header-args: :tangle ../src/transports/stdio.js
:END:

Stdio is a byte transport, like TCP. It uses the same =readFrame=/=writeFrame= framing. This is what makes a REPL "just another transport."

#+begin_src js
import readline from 'node:readline'
import { channel } from '../channel.js'
import { readFrame, writeFrame } from '../frame/jsonl.js'

export function fromStdio() {
  const rl = readline.createInterface({ input: process.stdin })
  const [read, write] = channel()
  rl.on('line', line => write.send(line + '\n'))
  rl.on('close', () => write.close())

  const [outRead, outWrite] = channel()
  outRead
    .map(writeFrame)
    .sink(data => process.stdout.write(data))
    .then(outWrite.close)
    .catch(outWrite.err)

  return [read.thru(readFrame), outWrite]
}
#+end_src

* Deployment

Deployment also has an abstract layer and a concrete one.

** Abstractly

A bassline system is deployed by making communication available somewhere and wiring local logic to it. Deployment is not where the system acquires a fixed command surface or a closed set of capabilities. It is where some part of the world becomes reachable for communication.

The reason this stays lightweight is the same reason the rest of the model stays lightweight: coordination is driven by message flow and local interpretation, not by a privileged deployment schema.

** Concretely

A bassline system can run as a daemon, a long-lived process listening on a socket. Interacting with it means obtaining a communication capability and exchanging messages.

*** The daemon is just a server with a sink

A boot script opens a socket and starts consuming connections. Each connection is a =[reader, writer]= pair. What the daemon does with those messages is determined by whatever logic is wired into the pipeline. There is no fixed set of capabilities.

#+begin_src js :tangle no
import { serve } from './transports/server.js'

const [connections, server] = serve({ path: '~/.bassline/sock' })

await connections.sink(([read, write]) => {
  read
    .map(handle)
    .sink(write.send)
})
#+end_src

The =handle= function is where all the logic lives. It could route messages onward, evaluate expressions, update state, or do nothing. The daemon just opens the door.

*** A REPL is just a transport

A command-line interface is a connection over stdio instead of a socket. =fromStdio()= gives you a =[reader, writer]= pair backed by stdin/stdout with the same framing as TCP.

#+begin_src js :tangle no
import { fromStdio } from './transports/stdio.js'

const [read, write] = fromStdio()
#+end_src

The downstream pipeline sees messages either way — same interface whether the transport is a socket, a WebSocket, or a terminal.

*** Custom command languages are just maps

Since a parser is a function from strings to messages, and =map= transforms a reader, a custom command language is just:

#+begin_src js :tangle no
stdin.map(parseBasslineShell)    // one language
stdin.map(parseJSON)             // another
stdin.map(parseS_expressions)   // another
#+end_src

The downstream pipeline sees messages either way.

*** Convention

By convention, a bassline daemon keeps its state under =~/.bassline/=, with =BASSLINE_HOME= as an override. The socket lives there. What else lives there (persistence files, logs, configuration) depends on what the boot script sets up.

The boot script is the only thing that's "configured" in the traditional sense. Everything else emerges from the messages the system receives after it starts listening.

export const isArray = v => Array.isArray(v)

export const isPromise = obj => obj instanceof Promise

export const isFunction = v => typeof v === 'function'
export const isPlainObject = obj => {
  if (obj == null) return false;
  return Object.getPrototypeOf(obj) === Object.prototype;

export const hasKeys = (obj, keys = []) => {
  if (isNil(obj)) return false
  const requiredKeys = isArray(keys) ? keys : [keys],
    objectKeys = new Set(Object.keys(obj))

  return requiredKeys.every(key => objectKeys.has(key))
}
