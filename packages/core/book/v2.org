* Introduction
This literate document contains the source code for the core of [[https://bassline.dev][Bassline]] v2.

Bassline is designed to be hacked on and modified, so we encourage people to read this!

** TLDR

Bassline is a system for partial information programming.

Programs in Bassline work with incomplete messages. They build local understanding from what they already know while acting on new information.

Anything outside your local perspective is encountered through communication.
When that communication yields information that matters, we observe it as a resource.
We do not need a complete account of what it is, where it is, or how it produces what we receive.

Identity, location, provenance, timing, and order are therefore not taken as settled facts.
They are local judgments made from partial information.
Different participants may have different grounds for believing them, and that is good.

The model never assumes a closed world, so growth uses the same mechanism as ordinary operation.
New message shapes, participants, and behavior do not require a separate extensibility system, they arrive as more messages to interpret.

* The Kernel

The kernel starts with messages and a local capability for communication.
In this book that capability is implemented with ports, a minimal set of capabilities for communication.
Keep in mind the important thing is the ability to exchange and observe information, not any particular interface shape.

For each part of the kernel, we will separate the abstract idea from the concrete implementation used in this book.
The abstract layer explains what shape of thing we are modeling.
The concrete layer shows one minimal JavaScript realization of that shape.

** Communication
:PROPERTIES:
:header-args: :tangle ../src/comm.js
:END:

*** Abstractly

Communication is the local capability to receive new information and contribute new information.
Bassline treats communication as an ongoing process in which participants coordinate by processing messages and inferring enough structure from what they know to continue.

Communication needs a shape that preserves decoupling. Producers should be able to contribute information without needing a fixed understanding of any consumer, and consumers should be able to build their own understanding from the flow they observe.

*** Concretely

In this book, communication is implemented as ports.

A port gives us 3 capabilities:

1. =send=

   Which let's us send a message to something

2. =recv=

   Which let's us pull a message from a local buffer, blocking until one is available.

3. =close=

   To ignore any future messages, stopping communication from our end.

A port is a minimal surface that faithfully implements what we care about from communication.

An important thing to note is that there is no builtin lifecycle propagation with ports.
This is because closing a port is a local decision made when a participant decides they aren't interested anymore, or that the conversation is not useful to them anymore.

Senders are not notified and their messages are dropped should they send to the closed port.
This ensures neither side requires knowledge of the other's state / status without the other side explicitly sharing this.

**** Port implementation

The port implementation is rather simple.

It maintains a buffer for messages, and a queue of promises to resolve.
We can give the buffer a fixed capacity, in which it will act as a sliding buffer, dropping the oldest messages.
Or if we give it a capacity of 0, it will not buffer any messages, requiring a listener actively be waiting for a message, dropping all others.

The only other thing to note is the local convenience of EOF.

EOF is a symbol sent through and used by local port consumers to indicate that the port closed.
It is not universal and will serialize over the wire meaningfully.
It only exists to make our lives simpler in js.
And it is trivial to build your own interpretation of what should signal EOF locally.

You cannot send EOF directly through a port, nor should you ever have to.
It should only be created internally inside of a port to notify a local consumer we are closed.

#+begin_src js
export const EOF = Symbol.for('$$BASSLINE_EOF$$')
export const isEOF = v => v === EOF
export function port(size = Infinity) {
  const buffer = []
  const waiters = []
  let closed = false
  const close = () => {
    closed = true
    for (const w of waiters) w(EOF)
    waiters.length = 0
  }
  const send = msg => {
    if (isEOF(msg)) throw new Error('Bassline EOF is reserved')
    if (closed) return
    if (waiters.length > 0) return waiters.shift()(msg)
    if (buffer.length >= size) buffer.shift() // sliding buffer
    if (size > 0) buffer.push(msg) // no buffer
  }
  const recv = () => {
    if (buffer.length > 0) return Promise.resolve(buffer.shift())
    if (closed) return Promise.resolve(EOF)
    return new Promise(resolve => waiters.push(resolve))
  }
  return { send, recv, close }
}
#+end_src

**** Using a port

The most common way to use a port, is inside of an endless async loop that exists when we recv EOF.

We define a helper for this called =consume=. It let's us build actor-like processes from our ports, and is convenient.

If you need to define more sophisticated control flow inside of the loop, just write the extra 3 lines. :)

#+begin_src js
export async function consume(recv, callback) {
  let msg
  while (true) {
    msg = await recv()
    if (isEOF(msg)) break
    await callback(msg)
  }
}
#+end_src

**** Nets
Now our ports look like "point-to-point" communication, however in Bassline we don't talk to "something", we observe information from our perspective.

This let's us do some neat things when it comes to communication.
For example, a common structure we use is a =net=.

A =net= is a local structure that gives us ports backed by any number of things.
Meaning that we build a compound communication interface without the consumers or producers ever knowing directly.
They might be able to tell if they see more information, but they can never know for sure.

This highlights that in bassline cooperating participants appear as a single participant, even if they are totally unaware of each other.

#+begin_src js
export function net() {
  const ports = new Set()

  function join(size) {
    const p = port(size)
    let closed = false
    ports.add(p)
    const send = msg => {
      if (closed) return
      ports.forEach(port => port !== p && port.send(msg))
    }
    const close = () => {
      closed = true
      ports.delete(p)
      p.close()
    }

    return {
      recv: p.recv,
      send,
      close,
    }
  }
  join.close = () => [...ports].forEach(p => p.close())
  join.send = msg => [...ports].forEach(p => p.send(msg))
  return join
}
#+end_src

**** Communication without input
Not all communication take input.

A clock is an example of a one-sided communication participant, it can say things, but will never listen.

It can be used with anything that wants a capability to receive information, and can be used for local chron jobs, scheduling, and similar things.

#+begin_src js
export const clock = (ms = 1000) => {
  const p = port(1)
  const tick = () => p.send({ ts: Date.now() })
  const interval = setInterval(tick, ms)
  tick()
  return {
    recv: p.recv,
    close: () => {
      clearInterval(interval)
      p.close()
    },
  }
}
#+end_src

** Messages
:PROPERTIES:
:header-args: :tangle ../src/messages.js
:END:
*** Abstractly

A message is a fragment of partial information. It is whatever can be locally held, passed around, inspected, and combined without requiring a complete picture of the world.

A message does not come with privileged meaning beyond what participants give it.
If provenance, correlation, naming, coordination hints, or other structure matters, it lives in the message like any other data.
Bassline does not want a separate metadata plane that is somehow more real than the information being exchanged.

*** Concretely

A message is a plain object with string keys. It can be empty, partially filled, or nested inside other messages.

The concrete representation is intentionally minimal. Plain objects are open-ended, nest naturally, and are easy to serialize, enrich, and inspect. That keeps the message lightweight and avoids forcing a closed protocol up front.

=message()= normalizes its input: plain objects pass through, =undefined= becomes ={}=, and anything else is wrapped as ={body: value}=.

=update= is auto-curried. With two arguments =(msg, fn)= it returns a new message. With one argument =(fn)= it returns a transform you can pass a message into.

#+begin_src js
import { isPlainObject } from './utils.js'

export const message = content => {
  if (content === undefined) return {}
  if (isPlainObject(content)) return { ...content }
  return { body: content }
}

export function updateWith(msg, fn) {
  return { ...msg, ...fn(msg) }
}

export function update(...args) {
  if (args.length === 1) {
    const [fn] = args
    return msg => updateWith(msg, fn)
  }
  if (args.length === 2) {
    const [msg, fn] = args
    return updateWith(msg, fn)
  }
  throw new Error(`invalid update arity: ${args.length}`)
}

export const isEmpty = msg => Object.keys(msg).length === 0
#+end_src

*** Exception Messages

We should not expect our systems to run smoothly, so we define these messages to indicate that some exceptional state has occurred while interpreting a message.

For now we define two kinds of exceptional states.

| condition | what it means                                |
|-----------+----------------------------------------------|
| Warning   | It's workable, but you should know something |
| Fault     | Something went wrong, and I cannot continue  |

**** Non Fatal Exceptions: Warnings

This means that something was able to complete what it needed to, but it has something to say about how it could be done better, or some remark on if there is a better way of doing it.

#+begin_src js
export const warning = reason => message({ type: 'warning', body: reason })
#+end_src

**** Fatal Errors: Fault
This indicates that processing cannot continue, and we must stop.

Unlike warnings, which are used to annotate the message being processed, we throw the fault message.

#+begin_src js
export class Fault extends Error {
  constructor(condition, msg, context = {}) {
    super(`fault: ${condition}`)
    this.condition = condition
    this.msg = msg
    this.context = context
  }
}
export const fault = (condition, msg, context) => {
  throw new Fault(condition, msg, context)
}
#+end_src

* Transports
As above, it helps to separate the abstract role of a transport from the concrete transport used in this book.

** Abstractly

A transport adapts some external medium into local communication capabilities. This matters because the programming model should not change just because information crossed a process boundary, a machine boundary, or a device boundary. Local and non-local communication differ in mechanics, but they should not require different conceptual tools.

** Concretely

Every transport produces the same thing: a port with =send=, =recv=, and =close=. What differs is the medium underneath and whether that medium carries raw bytes or discrete messages.

Byte transports (TCP sockets, stdio, serial) carry raw chunks. They need a framing layer to delimit and parse messages. Message transports (WebSocket, WebWorker/MessagePort) carry discrete messages natively and skip framing entirely.

*** Framing
:PROPERTIES:
:header-args: :tangle ../src/frame/jsonl.js
:END:

Framing is separated from any specific transport. =readFrame= bridges a byte-level =recv= to a message-level =send=: it consumes chunks, accumulates them in a buffer, splits on newlines, and emits parsed messages. =format= is a plain function that serializes a message as a JSON line.

#+begin_src js
import { message } from '../messages.js'
import { consume } from '../comm.js'

export function readFrame(recv, send) {
  let buffer = ''
  consume(recv, chunk => {
    buffer += chunk
    let nl
    while ((nl = buffer.indexOf('\n')) !== -1) {
      const line = buffer.slice(0, nl)
      buffer = buffer.slice(nl + 1)
      if (!line) continue
      try {
        send(message(JSON.parse(line)))
      } catch (e) {
        console.error('readFrame parse error: ', e)
      }
    }
  })
}

export const format = msg => JSON.stringify(msg) + '\n'

export default { read: readFrame, format }
#+end_src

=readFrame= fires off a =consume= loop in the background. One input chunk may produce zero or many messages. =format= is used on the outgoing side to serialize before writing.

*** Socket
:PROPERTIES:
:header-args: :tangle ../src/transports/socket.js
:END:

A socket is a byte transport. =fromSocket= creates a raw port for byte chunks, a message port for parsed messages, and bridges them through =frame.read=. Outgoing messages are formatted and written directly to the socket.

#+begin_src js
import net from 'node:net'
import { port } from '../comm.js'
import defaultFrame from '../frame/jsonl.js'

export function fromSocket(socket, frame = defaultFrame) {
  const raw = port()
  const msgs = port()

  socket.on('data', chunk => raw.send(chunk.toString()))
  socket.on('close', () => raw.close())
  socket.on('error', () => raw.close())

  frame.read(raw.recv, msgs.send)

  return {
    recv: msgs.recv,
    send: msg => socket.write(frame.format(msg)),
    close: () => {
      msgs.close()
      raw.close()
      socket.destroy()
    },
  }
}

export function connect(options = {}, frame = defaultFrame) {
  return fromSocket(net.createConnection(options), frame)
}
#+end_src

*** Serving (TCP)
:PROPERTIES:
:header-args: :tangle ../src/serve/tcp.js
:END:

A TCP server listens on a socket and produces a port of connections. Each connection is itself a port, produced by =fromSocket=.

#+begin_src js
import nodeNet from 'node:net'
import { fromSocket } from '../transports/socket.js'
import { port } from '../comm.js'

export function serve(options = {}, frame) {
  const p = port()
  const server = nodeNet.createServer(socket => {
    p.send(fromSocket(socket, frame))
  })
  server.listen(options)
  server.on('close', () => p.close())
  server.on('error', () => p.close())
  return {
    recv: p.recv,
    close: () => {
      p.close()
      server.close()
    },
    server,
  }
}
#+end_src

*** Serving (WebSocket)
:PROPERTIES:
:header-args: :tangle ../src/serve/ws.js
:END:

A WebSocket server wraps an existing =WebSocketServer= instance and produces a port of connections, matching the TCP serve API shape. The caller brings their own =WebSocketServer= — no =ws= dependency in core.

#+begin_src js
import { fromWebSocket } from '../transports/websocket.js'
import { port } from '../comm.js'

export function serve(wss) {
  const p = port()
  wss.on('connection', ws => p.send(fromWebSocket(ws)))
  wss.on('close', () => p.close())
  wss.on('error', () => p.close())
  return {
    recv: p.recv,
    close: () => {
      p.close()
      wss.close()
    },
    wss,
  }
}
#+end_src

*** WebSocket
:PROPERTIES:
:header-args: :tangle ../src/transports/websocket.js
:END:

A WebSocket is a message transport. Each =ws.send()= is one discrete message, so no framing is needed. This works in the browser with native =WebSocket=, in Node.js with the =ws= package, and for =RTCDataChannel= since it has the same event interface.

#+begin_src js
import { port } from '../comm.js'
import { message } from '../messages.js'

export function fromWebSocket(ws) {
  const p = port()
  ws.addEventListener('message', e => {
    try {
      p.send(message(JSON.parse(e.data)))
    } catch (e) {
      console.error('failed to parse: ', e)
    }
  })
  ws.addEventListener('close', () => p.close())
  ws.addEventListener('error', () => p.close())

  return {
    recv: p.recv,
    send: msg => ws.send(JSON.stringify(msg)),
    close: () => {
      p.close()
      ws.close()
    },
  }
}
#+end_src

*** WebWorker
:PROPERTIES:
:header-args: :tangle ../src/transports/worker.js
:END:

A =MessagePort= is a message transport that uses structured clone. Objects cross the boundary without serialization. Works with =Worker=, =MessagePort=, =SharedWorker.port=, and =BroadcastChannel=.

#+begin_src js
import { port } from '../comm.js'
import { message } from '../messages.js'

export function fromPort(messagePort) {
  const p = port()
  messagePort.onmessage = e => p.send(message(e.data))
  messagePort.onmessageerror = () => p.close()

  return {
    recv: p.recv,
    send: msg => messagePort.postMessage(msg),
    close: () => p.close(),
  }
}
#+end_src

*** Stdio
:PROPERTIES:
:header-args: :tangle ../src/transports/stdio.js
:END:

Stdio is a byte transport, like TCP, and uses framing internally to produce a port of messages.

#+begin_src js
import readline from 'node:readline'
import { port } from '../comm.js'
import defaultFrame from '../frame/jsonl.js'

export function fromStdio(frame = defaultFrame) {
  const raw = port()
  const msgs = port()
  const rl = readline.createInterface({ input: process.stdin })

  rl.on('line', line => raw.send(line + '\n'))
  rl.on('close', () => raw.close())

  frame.read(raw.recv, msgs.send)

  return {
    recv: msgs.recv,
    send: msg => process.stdout.write(frame.format(msg)),
    close: () => {
      msgs.close()
      raw.close()
      rl.close()
    },
  }
}
#+end_src

* Deployment (Draft)

This is a stub, so you can ignore this for now!

Deployment also has an abstract layer and a concrete one.

** Abstractly

A bassline system is deployed by making communication available somewhere and wiring local logic to it. Deployment is not where the system acquires a fixed command surface or a closed set of capabilities. It is where some part of the world becomes reachable for communication.

The reason this stays lightweight is the same reason the rest of the model stays lightweight: coordination is driven by message flow and local interpretation, not by a privileged deployment schema.

** Concretely

A bassline system can run as a daemon, a long-lived process listening on a socket. Interacting with it means obtaining a communication capability and exchanging messages.

*** The daemon is just a server with a recv loop

A boot script opens a socket and starts consuming connections. Each connection is a port. What the daemon does with those messages is determined by whatever logic is wired in. There is no fixed set of capabilities.

#+begin_src js :tangle no
import { serve } from './serve/tcp.js'
import { consume } from './comm.js'

const { recv } = serve({ path: '~/.bassline/sock' })

consume(recv, async conn => {
  consume(conn.recv, msg => conn.send(handle(msg)))
})
#+end_src

The =handle= function is where all the logic lives. It could route messages onward, evaluate expressions, update state, or do nothing. The daemon just opens the door.

*** A REPL is just a transport

A command-line interface is a connection over stdio instead of a socket. =fromStdio()= gives you a port backed by stdin/stdout with the same framing as TCP.

#+begin_src js :tangle no
import { fromStdio } from './transports/stdio.js'

const { send, recv } = fromStdio()
#+end_src

The downstream logic sees messages either way, regardless of whether the transport is a socket, a WebSocket, a terminal, or whatever else.

*** Convention

By convention, a bassline daemon keeps its state under =~/.bassline/=, with =BASSLINE_HOME= as an override. The socket lives there. What else lives there (persistence files, logs, configuration) depends on what the boot script sets up.

The boot script is the only thing that's "configured" in the traditional sense. Everything else emerges from the messages the system receives after it starts listening.

** Type Predicates

| Predicate     | Tests for                                             |
|---------------+-------------------------------------------------------|
| =isArray=       | =Array.isArray=                                         |
| =isNil=         | =null= or =undefined=                                     |
| =isPromise=     | =instanceof Promise=                                    |
| =isNumber=      | =typeof === 'number'=                                    |
| =isString=      | =typeof === 'string'=                                    |

#+begin_src js
export const isArray = v => Array.isArray(v)
export const isNil = obj => obj == null
export const isPromise = obj => obj instanceof Promise
export const isNumber = v => typeof v === 'number'
export const isString = v => typeof v === 'string'
export const isFunction = v => typeof v === 'function'
export const isNull = v => v === null
export const isPlainObject = obj => {
  if (obj == null) return false
  return Object.getPrototypeOf(obj) === Object.prototype
}
export const hasKeys = (obj, keys = []) => {
  if (isNil(obj)) return false
  const requiredKeys = isArray(keys) ? keys : [keys],
    objectKeys = new Set(Object.keys(obj))

  return requiredKeys.every(key => objectKeys.has(key))
}
export const not = predicate => value => !predicate(value)
export const constant = value => () => value
export const identity = value => value
